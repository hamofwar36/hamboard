# 동기화·백업 구조 개선 (v3 백업)

앱 버전은 1.0.13을 유지합니다. 이 ZIP은 Windows 소스 수정본이며 실행 파일이 아닙니다.

## 공통 데이터 정의와 중복 제거

- 새 로컬·클라우드 백업 모두 `CloudPayload.packUserState()`를 통해 동기화와 같은 `projectCloudUserData()`를 사용합니다.
- `cloudUserData`는 공통 사용자 데이터, `deviceStateDelta`는 공통 데이터로 만든 기본 상태와 원래 로컬 상태의 차이입니다. 전체 `state` 사본을 함께 저장하지 않습니다.
- `syncContext`에는 복원에 필요한 동기화 기준점의 차분을 별도로 보존합니다. 버전 기록과 네이티브 작업 기록도 보존합니다.
- 최상위 분류와 선별 저장되는 유틸리티 필드에 미분류 항목이 있으면 백업·동기화 송신을 중단합니다. 전체가 공유되는 컬렉션 내부 필드와 일반 설정은 자동으로 공유됩니다. 새 분류 추가 시 공통 정의 또는 명시적 기기 전용 분류를 갱신해야 합니다.

## 클라우드 백업 v3

- 전체 백업을 하나의 JSON 문자열로 만들지 않습니다. 공통 데이터, 기기 차분, 동기화 기준점, 버전 기록, 작업 기록, 자료 목록, GC 참조 목록을 페이지로 분리합니다.
- 페이지 목표 크기는 UTF-8 1MiB입니다. 레코드 하나가 더 크면 단독 페이지로 보존하며, 총용량 제한으로 쓰지 않습니다.
- 버전 기록은 SQLite 커서로 64개씩 읽고 페이지를 순서대로 저장합니다. 준비 과정에서 모든 버전 본문을 배열에 쌓지 않습니다.
- 내용 해시 기반 파일을 업로드한 뒤에만 최종 root를 게시합니다. 페이지 준비 파일과 SQLite pin은 중단된 업로드의 재시도에 사용됩니다. 완료·취소·재시작 시 불필요한 준비 파일을 정리합니다.
- 목록 응답에는 날짜·품질·개수와 root 참조만 보냅니다. v3 목록에는 이미지 objectKey 전체를 포함하지 않습니다. GC는 root의 페이지 참조와 objects 페이지만 읽고 상태·버전 본문은 읽지 않습니다.
- v3 복원은 버전 페이지 파일을 검증한 뒤 Rust에서 하나씩 읽어 기존 원자적 복원 트랜잭션에 삽입합니다. 버전 기록 전체를 웹뷰→Rust IPC JSON 한 벌로 다시 보내지 않습니다.
- v1/v2 클라우드 백업의 읽기·중단 작업 재시도는 유지합니다. 새 v3 백업은 수정된 앱에서 읽어야 합니다.

## 로컬 `.hbackup` 아카이브

- 새 내보내기는 단일 `.hbackup` 파일입니다. 기존 `.json` 백업 가져오기는 유지합니다.
- 아카이브는 작은 manifest, JSON 페이지, 원본 바이너리 자료로 구성됩니다. 이미지 base64 배열 및 전체 백업 JSON 직렬화를 제거했습니다.
- Rust가 1MiB 버퍼로 파일을 순차 복사합니다. 내보내기 완료 후 같은 디렉터리의 임시 파일을 최종 파일로 교체하므로 실패 시 기존 백업을 덮어쓰지 않습니다.
- 가져오기는 무작위 임시 경로에 순차 추출하고, 각 항목의 크기·SHA-256·중복 이름·파일 끝·참조를 확인합니다. 실패한 추출 파일은 제거합니다.
- 이미지 복원은 네이티브 파일 복사를 사용합니다. 자료 전체를 웹뷰 메모리로 읽지 않습니다. 버전 페이지는 DB 복원이 완료될 때까지 보존됩니다.
- 형식: `HMBACK03` 8바이트 magic, little-endian u64 항목 수. 각 항목은 u32 이름 바이트 수, UTF-8 이름, u64 본문 크기, 본문, SHA-256 32바이트 순입니다. 첫 항목은 `manifest.json`입니다. 압축·암호화 형식은 아닙니다.

## DB 및 자원 보호

- `cloud_json_pins` 생성은 Rust/Tauri migration 7로 이동했습니다. 기존 런타임 생성 테이블과 pin 행은 `IF NOT EXISTS`로 보존합니다. 프런트는 테이블 존재만 확인합니다.
- 고정 16MiB/64MiB 한도는 되살리지 않았습니다.
- Windows 실제 가용 디스크 공간을 조회합니다. 다운로드·페이지 준비·아카이브 생성/추출·이미지 복사·DB 복원 전에 필요한 공간과 64MiB 여유분을 확인하고, 전송 중에도 검사합니다. DB 복원에는 상태·버전 본문 크기의 3배를 기준으로 여유 공간을 요구합니다.
- 전체 조각 JSON을 합치는 기존 경로와 네이티브 대용량 읽기는 실제 가용 메모리를 기준으로 보수적으로 검사합니다. 선언 크기 초과·정수 범위 초과도 거부합니다. 자원 검사는 다른 프로세스의 할당을 예약하는 기능은 아니므로, 실제 I/O 실패 시에도 기존 복원 롤백을 사용합니다.
- 체크포인트 불완전 복구 차단, 공통 전송 작업 큐, 고유 임시 경로, 병렬 실패 시 진행 중 쓰기 종료 후 정리 등 이전 보호를 유지했습니다.

## 추가 수정: Rust 목록 오류·ID 차분·동기화 페이지 전송

- `google_drive.rs::list_sync_objects()`의 두 반환문에서 존재하지 않는 `manifest` 참조를 제거하고 `objects`를 그대로 반환합니다. 백업 전용 조건은 `backup_summary()` 안에만 남깁니다. 함수 범위 회귀 검사를 추가했습니다.
- 고유한 문자열 ID를 가진 객체 배열은 `id-array` 차분을 사용합니다. 순서 목록과 ID별 변경을 별도로 저장하여 맨 앞 삽입·삭제·정렬 때문에 기존 본문 전체가 차분에 복사되는 현상을 방지합니다. ID가 없거나 중복되는 일반 배열은 기존 인덱스 방식을 사용합니다.
- 새 차분 형식은 `state-delta-v2` / `cloud-state-delta-v2`로 구분합니다. 이전 v1 차분 및 전체 기준 상태 읽기를 유지합니다.
- `deviceStateDelta`와 `syncContext` 섹션은 `json-tree-v1` 페이지로 직렬화합니다. 객체·배열의 구조와 값을 순서대로 기록하고 긴 문자열도 32,768 UTF-16 단위로 나눕니다. 전체 차분 JSON 문자열을 만들지 않습니다. 이전 단일 scalar 섹션도 계속 읽습니다.
- 자동 동기화 checkpoint와 commit은 `source: value`로 전송 계층에 전달합니다. 전송 계층이 같은 tree codec으로 최대 약 1MiB 페이지를 순차 생성·전송하고, 모든 페이지가 완료되면 `hamboard-sync-pages` root를 게시합니다. 전체 checkpoint/commit stringify → Blob 분할 경로는 새 송신에서 제거했습니다.
- 수신은 페이지마다 크기·SHA-256을 검사하고 tree decoder에 반영합니다. 모든 조각을 Blob으로 합치거나 전체 JSON 문자열을 다시 parse하지 않습니다. 구조 불완전·중복 키·페이지 손상·누락이면 적용 전에 중단합니다.
- 동기화 GC는 새 root가 가리키는 모든 페이지를 보존합니다. 페이지 참조 형식이 불명확하면 삭제를 보류합니다. 중단된 업로드의 pin 보호와 내용 주소 재사용은 유지합니다.
- 이전 일반 JSON/조각 envelope 동기화 읽기는 유지합니다. 새 차분·백업 섹션 및 동기화 페이지 형식을 읽으려면 사용 기기를 이 수정본으로 업데이트해야 합니다. 구형 앱과 새 형식의 상호 운용은 보장하지 않습니다.
- Windows 네이티브 검증 명령 `npm run qa:native-windows`를 추가했습니다. Windows에서 `cargo check --locked --all-targets`와 `cargo test --locked --lib`를 수행하고 오류 시 실패합니다. 이 환경에서는 실행하지 못했습니다.

## 유지한 부분과 남는 한계

- 6시간보다 오래된 동일 조각의 새 복사본 생성 보호를 유지합니다. 원격 GC lease 전환 및 그에 따른 재업로드 절약은 이번 수정에 포함하지 않았습니다. 구형 기기가 lease를 무시하고 정리할 수 있으므로 기존 보호를 단순 제거하지 않았습니다.
- 현재 상태·동기화 기준점·완성된 차분 객체는 앱 구조상 메모리에 올라갑니다. tree 전송은 전체 JSON 문자열의 추가 생성을 없애는 조치이며, 전체 앱의 메모리 사용량이 데이터 크기와 무관해지는 것은 아닙니다. 단일 버전 레코드와 기존 백업의 공통 데이터 레코드에는 그 크기의 메모리가 필요합니다.
- 구형 JSON 백업 및 구형 chunk envelope를 읽는 호환 경로에는 전체 JSON 재구성이 남습니다. 새 형식 송신·수신은 페이지 방식이며, 개별 sync entity의 기존 payload 해시 계산/DB 저장은 해당 entity 단위 직렬화를 유지합니다.
- 상태·작업 기록의 최종 적용은 기존 IPC/DB 경로를 사용합니다. 모든 데이터 처리가 일정 메모리만 사용하는 구조로 바뀐 것은 아닙니다.

## 검증 결과

관련 JavaScript 검사 238개 통과:

- 동기화 138개
- 전송·복원 보호 15개
- 기존 대용량/호환 경로 21개 (20MiB/65MiB 모의 데이터 포함)
- 새 페이지·공통 정의·아카이브 연결 검사 19개
- ID 차분·동기화 tree 페이지·Rust 목록 범위 회귀 검사 15개
- 작품 저장소 17개
- 백그라운드 처리 13개

추가 SQLite 실험 2개 통과: 신규 DB의 migration 1–7 적용, 기존 pin 테이블과 행이 있는 DB의 migration 7 적용.

검증에는 실제 JS 함수의 페이지 준비→업로드 모의 실행→본문 복원, 분류 누락 거부, 해시 손상/누락 거부, 실패 후 재시도, 로컬 바이너리 경로 복원, 버전 페이지 보존, 목록 크기 독립성, GC 참조 전용 조회, 자원 부족 시 중단이 포함됩니다.

`validate-mobile-sync-model.mjs`는 `settings` 비포함을 기대하는 기존 검사에서 실패합니다. 수정 전 동일 소스에서도 같은 실패를 확인했으며 이번 작업 범위 밖의 모바일 규칙은 변경하지 않았습니다.

환경에 Rust/Windows 빌드 도구가 없어 새 네이티브 아카이브·디스크 검사·Windows 파일 교체 및 네이티브 버전 페이지 복원은 컴파일/실행 검증하지 못했습니다. 실제 Drive 다중 기기 연동과 Windows WebView 통합 실행도 미검증입니다. JS 테스트 통과를 Windows 실행 확인으로 해석하면 안 됩니다.
